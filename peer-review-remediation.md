Atomicity and Implementation Independence went through two passes: the first-pass fix narrowed each Spec-1 leak without eliminating it — the evaluator's own critique applied equally to that fix — so a second, targeted revision closed both properly rather than papering over a leak that just changed shape.

## Hidden architecture decisions (Workshop 2, Section C) — cross-reference

Two additional findings from the evaluator's "hidden architecture decisions" pass don't map to a single rubric dimension but bear directly on Implementation Independence and Scope Control above:

- **Reservation precedence as a fixed algorithm.** Spec-1 committed to "full precedence over general usage, with conflicting requests rejected outright" inside a Constraint, foreclosing alternatives (partial sharing, priority queues) before being named as a decision. In Spec-2 this is still asserted as a `[RISKY]` Assumption (SPEC.md line 102) — appropriately tagged as a risk-ranked working assumption rather than a hard requirement — and the concrete enforcement mechanism now lives in the architecture layer as AD-4 (row-level locking, `SELECT ... FOR UPDATE`, single-transaction commit), not in the spec kernel. This is correctly layered.
- **Token counting fixed as the metering unit inside a Capability.** Spec-1 fixed "token-level usage (prompt/generation tokens)" inside a Capability bullet rather than leaving *how* usage is measured open. Spec-2 keeps this in CAP-9 (SPEC.md lines 49–51) — task-spec2's own Problem Scope requires token-level metering, so demoting it to an open Assumption would contradict the assignment, not fix a leak — but the duplicate `[SAFE]` Assumption that used to restate the same fact (former line 98) was deleted, since a fact stated unambiguously once in a Capability doesn't need re-asserting as an Assumption too.

## Summary

All **8 of 8 rubric dimensions are resolved**. Six were resolved directly in the initial Spec 2 pass (Clarity, Scope Control, Verifiability, Consistency, Traceability, Decomposition Readiness); Atomicity and Implementation Independence required a second, targeted `bmad-spec` pass, because the first-pass fix for each initially narrowed the Spec-1 leak without eliminating it. That second pass is documented as a live agent/architect exchange — proposed directions, pushback, and the reasoning behind each final call — in `_bmad-output/specs/spec-gpu-governance/.memlog.md` (entries appended after the initial `spec finalized` event), which is the append-only audit trail this remediation matrix summarizes rather than duplicates.
